# 全市场任务互斥与终止

Web 全市场创建和恢复必须配置 `REDIS_URL` 并运行 `python -m web.worker`，不再由 API 进程后台执行，也不会退回线程。Compose 已有 `web-worker`，API 与 worker 必须使用相同 Redis、数据库和共享产物目录。

## 名额与状态

Redis 键为 `screening:active:YYYY-MM-DD:market`，日期采用 `Asia/Shanghai`。键值包含任务 ID 和随机持有者令牌，无自动过期时间。排队、运行和终止中均占位；用户、规则链、周期和股票池不影响互斥。多市场原子获取全部名额，完成一个市场后单独释放其名额。重复成功的同条件筛选仍按原数据库记录拒绝。

跨日不迁移锁：昨天任务不会阻止今天任务。失败、成功或确认终止后，只有匹配持有者才能删除锁。恢复任务竞争恢复当天的剩余市场名额。单股、自定义列表不受本限制影响。

冲突返回原业务错误结构，`error_code=SCREENING_MARKET_BUSY`，消息含市场和已有任务 ID。Redis 故障拒绝提交/恢复，不进行无锁筛选。

## 终止与异常

`POST /api/screening/jobs/{job_id}/cancel` 沿用现有用户鉴权。详情页提供“终止任务”；排队任务取消后不会开始筛选，运行任务进入 `cancelling`，RQ worker 确认执行进程退出后变成 `cancelled` 并释放名额。重复请求幂等，已完成结果保留；失败或已终止任务可继续处理未完成部分。

进程失联、RQ 记录缺失、Redis 错误等无法确认停止的情况保留锁，不凭心跳超时或日期自动清理。RQ 标记 abandoned 不等于进程已退出；必须先核实 worker 和执行进程，再处理遗留状态。不要直接删仍在运行任务的 Redis 键。停止已确认但回调失败时，可再次点击“确认终止状态”收尾；RQ 记录已丢失的情况需管理员停掉旧执行进程后核对数据库，按键值中的任务 ID/令牌定向清理，不批量清空 Redis。

Redis 应启用持久化、持久卷和 `noeviction`，不要将此 Redis 用作可随意清空的缓存。现有 Compose 开启 AOF。锁意外丢失时，创建流程还会检查数据库中当天该市场的进行中记录；这不是自动解除旧锁的依据。

## 上线顺序

1. 暂停全市场提交，停止旧 API 后台执行器及历史 agent/scheduler 等可能重复执行同一任务的入口，确认旧执行进程确已退出。不要仅重启 API 就认为筛选已停止。
2. 核对 `web_screening_jobs`、`screening_run_locks` 和子任务：历史进行中任务须先确认停止并人工收尾。没有 RQ 执行标识的旧任务不能由新接口假定已停止。
3. 备份数据库和 Redis，确认 Redis 持久卷/AOF 正常；部署相同版本 API、worker 和前端，启动 Redis、数据库、worker 后再开放 API 提交。
4. 用模拟任务核对冲突、终止确认和重新提交。本次开发验证未运行真实全市场筛选，不调用行情、搜索、LLM 或飞书；不修改规则链或默认 SQL。

本次没有新增行情、板块、搜索或 LLM 请求。以单市场 100 只股票为例，各供应商调用增量均为 0，筛选原有请求量不变；仅增加 Redis/RQ 和已有数据库状态操作。
